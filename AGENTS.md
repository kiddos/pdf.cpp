# AGENTS.md

Guidance for coding agents working on **pdfcpp**, a C++17 port of iText (Java) built with CMake.
The Java original lives in `reference/itext-java` (git-ignored, read-only — never edit it). `README.md` has the
user-facing overview, the Java→C++ module mapping and the "Not (yet) ported" list.

## Build and test

```sh
cmake -S . -B build                 # Release by default; -DPDFCPP_BUILD_TESTS=OFF / -DPDFCPP_BUILD_EXAMPLES=OFF
cmake --build build -j
ctest --test-dir build --output-on-failure
./build/tests/layout_test           # run one suite directly
```

- Dependencies: zlib and OpenSSL (libcrypto) are required; libjpeg/libpng are optional (images are parsed natively).
- A change is done when the build has **zero warnings** (`-Wall -Wextra`) and **all test suites pass**.
- Sources are globbed (`CONFIGURE_DEPENDS`): new `src/**/*.cc` files, `tests/*_test.cc` and `examples/*.cc` are
  picked up automatically — no CMake edits needed.
- Formatting: `clang-format-22 -i` with the repo's `.clang-format` (Google style, 2-space indent, 80 columns).
  `.clang-format-ignore` excludes generated files. Format every file you touch.
- Naming: `.clang-tidy` enforces Google naming (`readability-identifier-naming`). Configure with
  `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`, then `run-clang-tidy-22 -p build -quiet -clang-tidy-binary clang-tidy-22`
  must report nothing.

## Layout

| Path | Contents |
|------|----------|
| `include/pdfcpp/<module>/` | Public headers. Modules: `io`, `kernel`, `layout`, `barcodes`, `forms`, `signatures` |
| `src/<module>/` | Implementations, mirroring the header tree |
| `src/**/*.inc`, `src/io/generated/` | Generated tables (encodings, barcode/QR tables) — regenerate, don't hand-edit |
| `include/pdfcpp/kernel/pdf/pdf_name_constants.inc`, `src/kernel/pdf/pdf_name_constants.cc` | Generated by `tools/gen_pdfnames.py` from `PdfName.java` |
| `resources/` | AFM metrics + Adobe glyph list, embedded at build time by `cmake/EmbedResources.cmake`; read via `io::ResourceUtil::GetResource("font/afm/Helvetica.afm")` |
| `tests/` | One executable per `*_test.cc`, using the dependency-free `test_harness.h` (`TEST`, `EXPECT_*`) |
| `examples/` | Small programs (`hello_world`, `report`, `stamp`, `merge`, `extract_text`, `sign`) |
| `tools/` | Python generators that extract tables from the Java sources (`java_array.py`, `gen_pdfnames.py`) |

Namespaces: everything is in `pdfcpp`, with sub-namespaces `pdfcpp::io`, `pdfcpp::kernel`, `pdfcpp::layout`,
`pdfcpp::barcodes`, `pdfcpp::forms`, `pdfcpp::signatures`.

## Porting conventions (keep consistent)

- **Follow the Java code.** Port class by class from `reference/itext-java`, keeping the Java class names, method
  names (spelled in Google style, see below), constants and behaviour. That includes Java quirks, e.g. the inverted
  `ConvertTextSpaceToGlyphSpace`/`ConvertGlyphSpaceToTextSpace` and the MaskUtil penalty rules in the QR encoder. When
  the Java source is internally inconsistent, pick the correct variant and leave a comment.
- **Naming ([Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html#Naming)).** Java names map
  mechanically:
  - Types keep their name: `PdfDocument`.
  - Methods and functions are PascalCase: `getPage` → `GetPage`, `pdf_cast` → `PdfCast`. Exception: STL-compatible
    names (`begin`, `end`, `size`, `empty`, `what`, ...).
  - Constants with static storage and enumerators are `kPascalCase`: `ColorConstants.RED` → `color_constants::kRed`,
    `LayoutResult.FULL` → `LayoutResult::kFull`.
  - Java constant-holder classes become snake_case namespaces: `property::kFontSize`.
  - Locals, parameters and struct members are snake_case; class data members are snake_case with a trailing `_`.
  - `PdfName` constants are `k` + the Java name with its first letter capitalized (`PdfName::kAcroForm`,
    `PdfName::k3D`); the lowercase `a`/`r` become `kLowerA`/`kLowerR`.
  - Files are snake_case: `.h` headers with `PDFCPP_<PATH>_H_` include guards, `.cc` sources.
  - Exceptions are still used, deliberately deviating from Google style, because the port mirrors iText's error
    model.
- **Ownership:** PDF objects are `std::shared_ptr<PdfObject>` (`PdfObjectPtr`, `PdfDictionaryPtr`, …; downcast with
  `PdfCast<T>`). Objects hold a raw `PdfIndirectReference*` owned by `PdfXrefTable`; references own their target and
  `PdfXrefTable::ReleaseAll()` breaks cycles when the document closes. Don't introduce new reference cycles that
  outlive the document.
- **Strings:** Java `String` → UTF-8 `std::string`; `byte[]` → `pdfcpp::Bytes` (`std::vector<uint8_t>`). `PdfName`
  values are raw decoded bytes.
- **Layout API:** elements are `std::shared_ptr` created with `layout::Make<T>(...)`; fluent setters return `T&`;
  `Document::Add(IElement&)` uses `shared_from_this`. Renderers follow iText's model
  (`Layout()` → `LayoutResult` `kFull`/`kPartial`/`kNothing` with split/overflow renderers, then `Draw()`).
- **Exceptions:** `io::ITextException` / `kernel::PdfException`, with message constants mirroring the Java ones.
- **Generated tables:** extend `tools/` scripts and regenerate rather than typing tables by hand.
- **Untrusted input:** the reader must not hang or allocate unboundedly on malformed files (see the
  `MemoryLimitsAwareException` guards in `pdf_reader.cc`); add similar guards for new parsers.
- Style: Google C++ style (formatted by clang-format), include guards, self-contained headers.

## Testing and validation

- Add tests to the matching `tests/<module>_test.cc` (or a new `*_test.cc`). Where possible, port the assertions of
  the corresponding Java test and use its resources via `ReferenceDir()` (points into `reference/itext-java`).
- Tests that write files should write into the test's working directory (`build/tests`), not the repo root.
- Independent checks with poppler: `pdftotext`, `pdffonts`, `pdfinfo`, `pdfsig`, and `pdftoppm -png` to render pages
  and inspect them visually.
- Bit-exact comparisons against Java: Java 21 is available; compile the relevant Java package ad hoc (stubbing
  `com.itextpdf.commons` classes as needed) in a scratch directory and diff outputs — this is how the QR encoder was
  verified.

## Workflow

- Work module by module; pick the next item from README's "Not (yet) ported" list and update README when it lands.
- Commit per milestone with a `pdfcpp: <summary>` message; don't commit `build/`, `reference/` or generated test output.
